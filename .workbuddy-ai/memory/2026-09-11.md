## 第一性原理重构 hkg_flight（提交 40c8bbd）

用户判定项目被多轮第三方 agent 设计得过度防御，授权"相对激进的重构"，并允许
在不影响需求的前提下删除不必要的设计（先拿授权）。

### 执行顺序（这个顺序很重要）

1. **先固化 git 状态**（`b8e990d`）：`hkg_flight/terminal/`（3300 行）与 `tests/`
   此前**从未纳入版本控制**，而 `hkg_flight/tui.py` 已被删除。没有这一步，重构
   就没有回滚点。
2. **仓库清理**：33 份 agent 的指令/报告文档归档到 `docs/archive/`；删除 `build/`、
   `dist/`、`egg-info/`、`__pycache__/`、`.ruff_cache/`、`.agents/`、`.workbuddy-ai/tmp_*`。
   `.gitignore` 补 `.workbuddy-ai/tmp_*/`。
3. **拿授权**：用 AskUserQuestion 确认 4 个决策点（重构范围 / Python 版本 / 测试策略 /
   仓库清理），全部选"推荐"。
4. 重写 → 逐层验证 → 提交。

### 核心判断

- **poller 的 generation / publish-gate 是幽灵防御**：只有一个写者线程，`_refresh`
  从不与自身并发。反证很有力——原 `_run` 里 `_refresh_pending = False` 根本没持锁，
  这套"锁纪律"自己都不自洽。
- **deepcopy 被当成信仰**：`normalize_flights` 每轮产生全新 dict，发布后无人修改。
  改用"发布后不可变"约定 + 浅拷贝。`latest_revision()` 每 0.2s 深拷贝全部告警是明确的性能 bug。
- **信任边界画错了位置**：views 用 ~100 行做 rich-markup 白名单 + 标签平衡 + CJK
  字符簇切分，而数据源是 ASCII 短字符串。正确做法是清洗下沉到数据入口
  （`utils.clean_text` 剥控制字符），渲染层只转义 `[`。
- **双写渲染必然漂移**：`views.py` 和 `plain.py` 各有一套行渲染。合并为共用
  `flight_header()` / `flight_row()` 原语。
- **死代码被测试锁定**：第三方 agent 自己在评审报告里承认"删除会破坏测试套件，故保留"。
  这是自我强化的循环，必须连测试一起重写。

### 顺带修掉的真实缺陷

- `boarding_soon` 分支**永远不可达**（状态匹配表把 `board` 排在 `boarding soon` 之前）
- 只给数字的 payload（`{"no": "759"}`）会让 `query CX759` 失效；实测真实 HKIA API 的
  `no` 已含 IATA 前缀（`{"airline": "CKS", "no": "K4 701"}`），现兼容两种形态
- `COMMANDS.md` 记载的 `HKG_CACHE_DIR` / `HKG_WEB_PORT` 环境变量在代码中**根本不存在**

### 结果

- 源码 4677 → 3703 行（-20%）；测试 3482 → 2113 行但用例 82 → **222 全绿**
- `ruff check .` 通过；`compileall` 通过
- 真实 API 冒烟：417 departures / 415 arrivals，`query CX261` / `G63` / `BA15` 行为正确

### 工具坑

**Edit 工具在并行调用时会互相覆盖。** 同一文件（甚至不同文件）一次发多个 Edit，
有相当比例会静默丢失（工具返回 success 但内容没变）。表现为测试报出"旧代码"的
traceback。教训：**同一文件的多个修改必须串行发送**，改完用 grep/sed 核对。

另外 `pip install ruff` 装进了托管 Python（隔离目录，非用户环境），验证完已卸载。

## 第二轮：告警规则 + Web 重制（04:30 起）

### 核心缺陷

旧规则 `if old_value != new_value and new_value:` 把**首次分配**当成变化。
每个正常航班都会分到机位 → 一天几百个航班就有几百条告警；而真正的 **release**
（`N24 -> -`，new 为空）反而被 `and new_value` 漏掉。触发条件恰好写反了。

### 新模型：以"原始分配"为基线

`AlertManager` 内部维护 `_baseline[(key, field)] -> 首次分配值`：

- `- -> N24` 首次分配 → 不告警，只记基线
- `N24 -> -` release → 告警 `N24 -> —`
- `N24 -> S47` change → 告警 `N24 -> S47`
- `N24 -> - -> S47` → 告警 `N24 -> S47`（保留原始基线，绝不显示 `- -> S47`）
- `N24 -> S47 -> N24` 回到基线 → **清除**告警
- departed / landed / cancelled → 清除该航班全部告警与基线

`old_value` 恒为原始分配值，所以"释放后重分配"读起来仍是"从原机位改到新机位"。
状态判定改用 `utils.status_category()`，不再做子串匹配 `"departed" in raw`。

### 删掉的过度设计

- **active/history 双表**：`get_history()` 只有测试和清理脚本消费，没有任何前端读取。
  改为单一列表，`alerts.json` 现在就是一个 list。
- `_CLEARING_STATUSES` 子串表 → `status_category()` 的稳定类别。
- `cache.read_alerts()` 返回 `{active, history}` → 返回 list（仍兼容旧 dict 形态）。
- 新增 `retain_date(date_str)`：poller 每次刷新后清掉非当前数据日期的告警，
  否则跨日长跑会残留昨天的行。

### 前端重制

- TUI 告警页：裸文本行 → 对齐表格 `CHANGED / FLIGHT / CHANGE / STATUS`，状态着色，
  详情页显示变动 + 当前航班。
- CLI `alerts`：复用 `views.alert_header/alert_line`（原来自己另写一套）。
- Web：`web.py` 单页仪表盘重写，双视图 Flights / Gate·Stand Changes，状态药丸、
  数据源健康点、30s 自动刷新；`/api/stats` 扩展为健康信息。

### 顺带修掉的真实 bug

- **宽屏（≥120 列）告警页必崩**：`views._wide_body` 对非航班页统一用 `row['code']`，
  而 alert/airline 行结构不同 → `KeyError: 'code'`。已按页分派，并补了回归测试。
  这个 bug 之前一直存在，只是宽屏告警页从没被测过（测试只用 100 列）。

### 失实文档（又修一遍）

- `COMMANDS.md` 的 `HKG_CACHE_DIR` / `HKG_WEB_PORT` **仍在**（上一轮声称修了但没修）→ 已改。
- `COMMANDS.md` 声称"今日数据缓存 5 分钟 / 历史数据 24 小时" → 实际航班数据**无 TTL**，
  每次直连 API 并写穿缓存；只有航司元数据 24h。已更正。
- `cleanup_alerts.py` 在新数据形态下会崩（按 dict 读）→ 重写为 60 行的查看/清空工具。

### 结果

- 测试 222 → **229 全绿**（+7 条规则/宽屏回归），`ruff check .` 通过
- Web 端到端冒烟：`/` 返回仪表盘、`/api/alerts` 返回 `CX759 GATE 62 → 63`、
  `/api/stats` 报 `source=api, flights=1, alerts=1`
- 静态预览：`.workbuddy-ai/preview/dashboard-preview.html`（stub 掉 fetch，可直接打开）

## 第三轮：数据身份 + 渲染修正（23:00 起）

用户贴了 `query 067` / `query 862` 的实际输出，同一航班号同一时刻出现两行，像重复。

### 两个独立缺陷叠在一起

**缺陷一：跨日结果看不出日期。** `_search_dates` 在 22:00–01:59 返回相邻两天
（设计如此，为了找到次日红眼航班），但表格只渲染 `HH:MM`。于是 `ZE862 00:05`
在 09-11 和 09-12 各有一条，看起来完全一样。

**缺陷二：`make_flight_key` 不含方向 —— 会真丢数据。**
`{date}_{flight_number}` 这个 key 把同一天的同号到达和出发视为同一条。实测 7 天
缓存，**每天稳定 6 个**这样的航班号（UA820/UA821/UA152/UA153/ET644/ET645）——
UA820 从 LAX 落地、再飞往 BKK。

后果（全部实测确认）：

| 位置 | 后果 |
|---|---|
| `cli.search_flights` 按 key 去重 | 静默丢一半。`query UA820` 只出 2 行（到达×2天），07:40 → BKK 整个消失 |
| `poller._refresh` 的 `old_map` | 同号双向塌陷，可能拿到达记录去 diff 出发记录 |
| `alerts._drop_key` | 到达航班落地连带抹掉同号出发航班的告警 |
| `alerts.json` | 6 条缓存告警**全部**落在碰撞航班号上，已污染 |

修复：key 改为 `{date}_{ARR|DEP}_{flight_number}`。`alerts.json` 已备份
（`alerts.json.pre-direction-key.*.bak`）后清空 —— 旧 key 无法与新记录对账，
会变成永不消解的幽灵告警。

### 渲染修正

- **stand 不再补前缀**：HKIA 的 `stand` 自带区域字母（`W69`/`D201`/`S25`），
  旧代码 `f"S{stand}"` 渲染出 `SW69`。web 端更冗余：`"Stand " + f.stand` → `Stand W63`。
  现在 CLI 原样显示 `W63`，web 去掉前缀（列头已写 Gate / Stand）。
- **ROUTE 列标方向**：`← KIX`（到达）/ `→ KIX`（出发）。裸机场码在混合列表里有歧义。
- 跨天结果插入日期分隔线 `-- 2026-09-11 ----`；`_print_table` 与 `paginate_records`
  合并到共用的 `_print_flight_rows`（顺带去掉重复的 header+rule 循环）。
- `query` 标题 `862 flights — 5 flight(s)` → `Query '862' — 5 flight(s)`。

### 数据字段事实（7 天 1928/1755 条，零例外）

| 字段 | 形状 | 出现于 |
|---|---|---|
| `gate` | 纯数字 `68` | 只有出发 |
| `stand` | 字母+数字 `W63` | 只有到达 |

**不要再给 stand 补字母前缀**，也不要给 gate 补数字以外的假设。

### 顺带修掉的测试缺陷

`test_search_dates_covers_today_by_default` 断言"默认只搜今天"——但它**只在白天通过**，
夜里必挂（跨午夜是设计行为）。已给 `_search_dates` 加可注入的 `now`，并补跨午夜用例。
教训：时间相关的纯函数要把"现在"作为参数，否则测试本身就是定时炸弹。

### 验证

- 测试 229 → **240 全绿**（+11），`ruff check .` 通过，`compileall` 通过
- 新增回归测试 `test_an_arrival_landing_does_not_clear_its_departure`，
  并**反向验证过**：把 key 打回旧格式后该测试失败（0 != 1），确认它真能抓住 bug
- 实跑 `query 862` / `query 067` / `query UA820`：日期分隔 + 方向箭头 + stand 原样；
  UA820 从 2 行变 4 行，丢失的出发回来了
