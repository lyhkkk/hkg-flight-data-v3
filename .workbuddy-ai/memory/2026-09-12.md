# 2026-09-12

## TUI 折行修正（第四轮）

用户贴了两张手机上的 TUI 截图。表面症状：状态串里的 `(12/09/2026)` 独占一行、
且被截成 `(12/09/20…`。查下来是**四个独立缺陷**叠在一起。

### 缺陷一（核心）：渲染宽度 ≠ widget 内容宽

`theme.tcss` 里 5 个整宽 widget 都是 `padding: 0 1`，widget 内容宽 =
`size.width - 2`；而 `body_lines` 按 `size.width` 渲染。实测 **25/26 行正好顶满
`width`**。Textual 不会裁掉溢出的 2 格，而是按**词**折行——把整个最后一个词推到
下一行，所以 `At gate 23:47 (12/09/2026)` 的日期整块掉下去了。

修复：**去掉所有横向 padding**，让「渲染宽度 = 终端宽度」成为唯一来源；gutter 改由
渲染层提供（header/nav/footer 自带前导空格，航班行自带两格 marker）。
理由：否则 CSS 的 padding 与 Python 宽度常量要永远手工同步，必然漂移。

### 缺陷二：顶栏/导航/底栏不看宽度

header 65 格、nav 74 格、footer 66 格，手机 55 列下全部折行；footer 折掉的是
`q Quit`。修复：三条都加 `width` + 阶梯写法（`views.fit`）。同时删掉 `cli._fits`
（与 `views.fit` 重复），统一一处实现。

### 缺陷三：`layout` 纯比例权重饿死状态列

55 列下 TIME 分 11 格（只需 5）、TERM 分 8 格（只需 3），STATUS 只有 22 格却要放
**26 字符**（真实最长 `At gate 23:47 (06/09/2026)`）。100 列下更糟：宽屏 6 列布局里
status 权重 4/18，**终端越宽状态越看不清**。

修复：列定义升级为 `(label, weight, minimum)`，先给最小宽度、余量再按权重分，
放不下时退回纯权重。表头与数据行读同一张表。

**关键陷阱：表头标签不能给自己单独的最小宽度。** 我第一版写成
`max(minimum, text_width(label))`，结果 `GATE/STAND`（标签 10 格）比数据（5 格）
大，表头与数据行整体错位 1 格。正确做法是把 10 写进列定义，让表头永不出现省略号。
`TERM` 同理（标签 4 > 数据 3）。

### 缺陷四：body 高度多算 1 行

`available = height - 3`，而 `#body` 实际是 `height - 4`。单行档下永远多裁 1 行。
修复：`views.CHROME_ROWS = 4`，`textual_app._body_height()` 也用它，并用测试解析
`theme.tcss` 锁住这个数。

### 结果

手机 55×30：chrome 6 → 4 行，可视航班 8 → 12 条，26 字符状态从 48 列起完整显示
（修复前 100 列都放不下）。测试 255 → **276 全绿**。

### 反向验证（三个都做了）

- 列最小宽度：旧的 2 元组写法把状态截成 `At gate 23:47 (06/09/2…`，新的完整 ✓
- 高度常量：把 `CHROME_ROWS` 打回 3，6 个用例各超 1 行 ✓
- widget 宽度：55 列下 25/25 行顶满，有 padding 时全都会被折行 ✓
  → **这条归因后来被第五轮订正了，见下。**

### 教训

**给渲染函数加「输出 ≤ 请求宽度」的不变量测试，会顺带挖出别处的同类 bug。**
这一轮又挖出 `size_hint` 文案是唯一没做自身截断的渲染器。

**另一个陷阱：我第一版测试用紧凑档（width 55）验证高度预算，被 `_window` 的
floor 掩盖了 off-by-one。** 同一不变量要在**两个档位**都测——紧凑档的两行 row
会把余数吃掉，恰好藏住边界错误。

### 工具坑

`_cell(char)`（几何辅助）与新写的 `_cell(columns, label, value)` 重名，后者静默覆盖
前者，61 个测试报 `TypeError: _cell() missing 2 required positional arguments`。
教训：在已有模块里加私有辅助函数前，先 grep 名字。

## TUI 真机验证（第五轮，装上 Textual 8.2.8）

第四轮全是离线推的。装上 Textual（Python 3.14）后真跑起来，发现两处结论要改。

### 订正一：`export_screenshot()` 是**按样式段**输出，不是按行

SVG 里每一行不是一个 `<text>`，而是**每个样式段一个 `<text>`**。航班行的状态单独
着色，所以它和前半段是**同一个 `y` 上的两个 `<text>`**（状态在 `x=280.6` = 第 23 格）。

把每个 `<text>` 当一行读，会**凭空造出折行**——我第一版助手就是这么写的，于是
「状态独占一行」的假象在**已经修好的**代码上又复现了一次，害我以为修复没生效。

正确读法：按 `y` 分组，再用 `x` 把每段拼回它所在的格。单元格宽是字体度量（12.2），
不写死——Rich 给每一行在右边缘补一个 marker 段，`max(x) / 终端宽度` 就是它。

**通用教训：把「一屏文本」拆成行时，先确认渲染器是按行还是按样式段输出的。**

### 订正二：55 列下 `padding: 0 1` 折的是**分隔线**，不是航班行

实测（`padding: 0 1`，55×30）：屏幕画出 **31 行**，逻辑行 25 行——多的 1 行是
**分隔线**。分隔线是 `"-" * width`，**没有一个空格可以吸收溢出**，所以内容宽少 2 格
就立刻裂成两行。而航班行有 6 格尾部空格兜着，55 列下（有效内容 49 格）反而没折。

所以「内容宽 ≠ 渲染宽」确实是必须修的不变量违例（分隔线就是铁证），但**航班行本身
在那个宽度下没折**。手机截图里日期被挤下去的主因是**缺陷三**（STATUS 被权重饿死到
22 格，先截成残段）叠加**缺陷二**（chrome 折行把 body 挤掉 2 行）。修复方向没错，
归因需要修正。已在 `PROJECT-STATUS.md` / `SPEC.md` 标注。

### 真机几何（Textual 8.2.8）

| 断言 | 结果 |
|---|---|
| `#body.content_size.width == app.size.width` | ✅ 55/80/100/45/120 全部成立 |
| `#header`/`#nav`/`#footer` | ✅ 每个都是 `Size(width=W, height=1)` |
| `#body.size.height` | ✅ `app.size.height - 4` = `views.CHROME_ROWS` |
| 全部 widget padding | ✅ `0 0` |

### 测试

`tests/test_terminal_textual.py` 的助手重写（`screen_runs` + 按 `y` 重建的
`screen_lines`），`TestTextualGeometry` 从 3 条扩到 6 条，其中两条是反证：

- `test_every_rendered_line_reaches_the_screen_intact` —— **最强的一条**：`views`
  产出的每一行（4 条 chrome + body）都必须原样成为屏幕上的**一行**，42/55/80/120
  列都扫
- `test_a_long_status_stays_on_its_flight_row` —— 42/45/48/55/80/100/120 列下状态
  都和航班号同行，且没有孤立的日期残段
- `test_a_word_that_does_not_fit_moves_to_its_own_row` —— 反证：故意喂放不下的词
- `test_the_old_padding_would_have_wrapped` —— 反证：装回 `padding: 0 1`，分隔线必须裂开

**反向验证（4 组）**：去掉 STATUS 最小宽度 → 正测挂；装回「每段当一行」的旧助手 →
正测 + 端到端挂；让渲染行比 widget 宽 → 端到端挂；让溢出刚好放得下 → 反证找不到那个词。

**测试卫生**：触发重绘用 `app.revision += 1`（reactive，app 自己的机制）而不是
`app._refresh_view()`；比较文本用 `views.strip_tags()` 而不是读 `app._color`。
测试不碰私有成员。

结果：`unittest` 276 → **283**，装了 Textual **0 skipped**，没装 12 skipped；
两个解释器都全绿。

## 第五轮：第三方代码审查的核实与落地（de4793d 之后）

一份外部审查（`hkg-flight-data-notes/review-de4793d.md`）对 de4793d 提了 5 条。
逐条核实后：**方向对（提交确实站得住），但严重度排布是错的** —— 唯一真正可操作
的那条被标成「PRE-EXISTING、不在范围内」放在第一位，而它主打的「latent bug」
**触发不了**。

### 核实结论

- **编码问题（审查 #1）**：机制属实，但**归因错层**。本机 `GetACP() = 1252`，
  `→`(U+2192) 在 cp1252/cp437 下无法编码（GBK 可以）。但 WorkBuddy 的 shell 里
  `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8`，所以**项目自己的验证命令永远看不到它**
  （283/OK）。强制 `PYTHONUTF8=0 PYTHONIOENCODING=cp1252` 可精确复现
  `cli.py:225 print(line)` ← `cli.py:287`。
  **这不是测试问题，是产品问题**：整个包里没有任何 stdout 编码防护，
  真实用户在 cp1252 控制台上跑 CLI 会直接崩。审查建议「在测试里设
  PYTHONIOENCODING」是把真崩溃藏起来，修错了层。
- **`cell` 校准（审查 #2）**：**前提错误**。那个「右边缘 marker run」
  **就是 Rich 每行结尾的换行 run**（`text == '\n'`，位于 `x = 宽度 × cell`）。
  实测：换行 run 数 = 绘制行数 − 2（首行装饰行和最后一行没有）。
  55 列下 31 行 → 29 个；空 alerts 页 / 无匹配搜索 / 20×10 / 120×30 全都存在。
  只要画了 ≥3 行 `max(x)` 一定来自它，而本 app 永远至少 4 行 chrome。
  **审查设想的「空 body 后落到内容 run」不可达**。
- 审查 #3（`html.unescape`）、#4（正则）方向对但**举例偏了**；
  #5（死代码）属实但无价值；建议 #4（加注释）**已经做过了**（第 91–93 行）。
- 审查把测试名写成 `test_paginate_tests_navigation`，实际是
  `TestCLIRendering.test_paginate_records_navigation`。
- 审查声称 scope 含 `SPEC.md` / `PROJECT-STATUS.md` / memory，但**一条意见都没给**。

### 审查漏掉的两点（已修）

1. **`screen_lines` 里的 `views.text_width(line)` 会剥掉 rich markup** —— 正是
   本项目记过的那个坑。若某个**非首个** run 的前缀含 `[...]`，padding 会算多、
   列错位。实测目前不可达（nav 行是单一样式 run），但比审查列的那些「前瞻性
   风险」更贴近本项目的已知雷区。
2. **属性正则没锚定**：`re.search(r'x="..."', attrs)` 会被**以 x 结尾的属性名**
   误匹配 —— `index="5"` 里就含 `x="`（已反证：旧模式真的抓出 `'5'`）。
   这比审查担心的「属性值含 `>`」更可能发生。两者都已修。

### 实际改动（4 个文件，286 用例全绿）

- `hkg_flight/cli.py`：新增 `make_output_robust()`，在 `main()` 开头调用。
  **只改 `errors="replace"`，绝不改 encoding** —— 一个 `?` 占一格，保住
  「渲染行 ≤ 请求宽度」不变量；重编成 UTF-8 反而会破（cp1252 控制台会把
  箭头的 3 个字节渲染成 3 个字形）。
- `tests/test_terminal_textual.py`：`_unescape` 换成 `html.unescape` +
  **`\xa0` → 空格归一化**（关键！见下）；属性正则加锚定 + 引号感知；
  新增校准守卫与拼接守卫。
- `test_hkg_flight.py`：分页测试改用 `redirect_stdout` 捕获（顺带止住了
  往控制台倒航班表）；新增 3 条编码测试（含 1 条反证 + 1 条 `main()` 接线测试）。
- `SPEC.md`：记下箭头在 cp1252/cp437 上退化成 `?`、方向信息丢失但行仍对齐。

### 新踩的坑（重要）

**`html.unescape` 会把 `&#160;` 变成 U+00A0（不换行空格），不是普通空格。**
旧的 4 实体助手是映射成普通空格的。直接换 `html.unescape` 会让 `screen_lines`
产出的每一行都含 nbsp，于是 `assertIn`（拿 `views` 的普通空格行去比）**全线挂**，
而且屏幕看起来完全一样 —— 表现为 42 列先挂（其实是所有宽度都挂）。
**换 `html.unescape` 必须跟 `.replace("\xa0", " ")`。**

### 反向验证（6 组，全部按预期失败）

1. 不调 `make_output_robust()` → 箭头写入抛 `UnicodeEncodeError`（正测有载）
2. 去掉 `main()` 里的调用 → `stream.errors` 仍是 `'strict'`（接线测试有载）
3. 滤掉换行 run → 校准守卫报「rightmost run is content ('FlightBoardApp' at x=343.0)」
   （若不守，cell 会算成 343/55=6.24 而不是 12.2，**49% 误差**）
4. 旧的未锚定 `x="` 模式 → 真的把 `index="5"` 抓成 `'5'`
5. 旧的 `<text([^>]*)>` → `data-x="1>2"` 被切碎成 `(' class="a" data-x="1', '2" x="7" y="0">hi')`
6. 把拼接偏移 +20 列（校准不动）→ 宽度守卫独立报 `63 > 55`
   （证明两个守卫各自有载，不是冗余）

结果：`unittest` 283 → **286**；3.14（有 Textual）**0 skipped**，3.13（无）12 skipped；
`ruff` 全绿。
