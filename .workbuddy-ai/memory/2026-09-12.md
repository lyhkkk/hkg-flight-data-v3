# 2026-09-12

## TUI 折行修正（第四轮）

用户贴了两张手机上的 TUI 截图。表面症状：状态串里的 `(12/09/2026)` 独占一行、
且被截成 `(12/09/20…`。查下来是**四个独立缺陷**叠在一起。

### 缺陷一（核心）：渲染宽度 ≠ widget 内容宽

`theme.tcss` 里 5 个整宽 widget 都是 `padding: 0 1`，widget 内容宽 =
`size.width - 2`；而 `body_lines` 按 `size.width` 渲染。实测 **25/26 行正好顶满
`width`**。Textual 不会裁掉溢出的 2 格，而是按**词**折行——把整个最后一个词推到
下一行，所以 `At gate 23:47 (12/09/2026)` 的日期整块掉下去了。

修复：**去掉所有横向 padding**，让「渲染宽度 = 终端宽度」成为唯一来源；gutter 改由
渲染层提供（header/nav/footer 自带前导空格，航班行自带两格 marker）。
理由：否则 CSS 的 padding 与 Python 宽度常量要永远手工同步，必然漂移。

### 缺陷二：顶栏/导航/底栏不看宽度

header 65 格、nav 74 格、footer 66 格，手机 55 列下全部折行；footer 折掉的是
`q Quit`。修复：三条都加 `width` + 阶梯写法（`views.fit`）。同时删掉 `cli._fits`
（与 `views.fit` 重复），统一一处实现。

### 缺陷三：`layout` 纯比例权重饿死状态列

55 列下 TIME 分 11 格（只需 5）、TERM 分 8 格（只需 3），STATUS 只有 22 格却要放
**26 字符**（真实最长 `At gate 23:47 (06/09/2026)`）。100 列下更糟：宽屏 6 列布局里
status 权重 4/18，**终端越宽状态越看不清**。

修复：列定义升级为 `(label, weight, minimum)`，先给最小宽度、余量再按权重分，
放不下时退回纯权重。表头与数据行读同一张表。

**关键陷阱：表头标签不能给自己单独的最小宽度。** 我第一版写成
`max(minimum, text_width(label))`，结果 `GATE/STAND`（标签 10 格）比数据（5 格）
大，表头与数据行整体错位 1 格。正确做法是把 10 写进列定义，让表头永不出现省略号。
`TERM` 同理（标签 4 > 数据 3）。

### 缺陷四：body 高度多算 1 行

`available = height - 3`，而 `#body` 实际是 `height - 4`。单行档下永远多裁 1 行。
修复：`views.CHROME_ROWS = 4`，`textual_app._body_height()` 也用它，并用测试解析
`theme.tcss` 锁住这个数。

### 结果

手机 55×30：chrome 6 → 4 行，可视航班 8 → 12 条，26 字符状态从 48 列起完整显示
（修复前 100 列都放不下）。测试 255 → **276 全绿**。

### 反向验证（三个都做了）

- 列最小宽度：旧的 2 元组写法把状态截成 `At gate 23:47 (06/09/2…`，新的完整 ✓
- 高度常量：把 `CHROME_ROWS` 打回 3，6 个用例各超 1 行 ✓
- widget 宽度：55 列下 25/25 行顶满，有 padding 时全都会被折行 ✓
  → **这条归因后来被第五轮订正了，见下。**

### 教训

**给渲染函数加「输出 ≤ 请求宽度」的不变量测试，会顺带挖出别处的同类 bug。**
这一轮又挖出 `size_hint` 文案是唯一没做自身截断的渲染器。

**另一个陷阱：我第一版测试用紧凑档（width 55）验证高度预算，被 `_window` 的
floor 掩盖了 off-by-one。** 同一不变量要在**两个档位**都测——紧凑档的两行 row
会把余数吃掉，恰好藏住边界错误。

### 工具坑

`_cell(char)`（几何辅助）与新写的 `_cell(columns, label, value)` 重名，后者静默覆盖
前者，61 个测试报 `TypeError: _cell() missing 2 required positional arguments`。
教训：在已有模块里加私有辅助函数前，先 grep 名字。

## TUI 真机验证（第五轮，装上 Textual 8.2.8）

第四轮全是离线推的。装上 Textual（Python 3.14）后真跑起来，发现两处结论要改。

### 订正一：`export_screenshot()` 是**按样式段**输出，不是按行

SVG 里每一行不是一个 `<text>`，而是**每个样式段一个 `<text>`**。航班行的状态单独
着色，所以它和前半段是**同一个 `y` 上的两个 `<text>`**（状态在 `x=280.6` = 第 23 格）。

把每个 `<text>` 当一行读，会**凭空造出折行**——我第一版助手就是这么写的，于是
「状态独占一行」的假象在**已经修好的**代码上又复现了一次，害我以为修复没生效。

正确读法：按 `y` 分组，再用 `x` 把每段拼回它所在的格。单元格宽是字体度量（12.2），
不写死——Rich 给每一行在右边缘补一个 marker 段，`max(x) / 终端宽度` 就是它。

**通用教训：把「一屏文本」拆成行时，先确认渲染器是按行还是按样式段输出的。**

### 订正二：55 列下 `padding: 0 1` 折的是**分隔线**，不是航班行

实测（`padding: 0 1`，55×30）：屏幕画出 **31 行**，逻辑行 25 行——多的 1 行是
**分隔线**。分隔线是 `"-" * width`，**没有一个空格可以吸收溢出**，所以内容宽少 2 格
就立刻裂成两行。而航班行有 6 格尾部空格兜着，55 列下（有效内容 49 格）反而没折。

所以「内容宽 ≠ 渲染宽」确实是必须修的不变量违例（分隔线就是铁证），但**航班行本身
在那个宽度下没折**。手机截图里日期被挤下去的主因是**缺陷三**（STATUS 被权重饿死到
22 格，先截成残段）叠加**缺陷二**（chrome 折行把 body 挤掉 2 行）。修复方向没错，
归因需要修正。已在 `PROJECT-STATUS.md` / `SPEC.md` 标注。
