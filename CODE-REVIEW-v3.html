一、P1 — 影响用户体验的问题（4 项）

F1. Poller.stop() 竞态条件 — 线程可能永远不会终止 P1 并发

poller.py:50-55
# 当前代码
def stop(self):
    self._stop_event.set()
    if self._thread:
        self._thread.join(timeout=5)  # 只等 5 秒

_run() 中 self._stop_event.wait(self.poll_interval) 默认等待 30 秒。join(5) 超时后线程仍在运行，旧线程永远不会被终止，造成资源泄漏。下次调用 start() 时 is_alive() 检查会阻止新线程启动，但旧线程仍占用资源。

修复建议：在 stop() 中将 poll_interval 临时设为 1 秒再 join；或在 _run() 的循环末尾直接 if self._stop_event.is_set(): break。

F2. Web 前端无错误处理 — API 异常导致白屏 P1 前端

web.py:348-353 (内嵌 JS)
async function loadFlights() {
    const res = await fetch(`${API_BASE}/flights`);
    allFlights = await res.json();  // 若返回 {"error":"..."} 则 allFlights 变为对象
    renderFlights();                // → flights.filter(...) 抛 TypeError → 白屏
}

三个缺陷叠加：(1) 无 try/catch — 网络错误静默抛异常；(2) 未检查 Array.isArray(data) — 参数校验失败时 allFlights 变为对象；(3) 未检查 res.ok — 500 等错误仍尝试解析。

修复建议：
async function loadFlights() {
    try {
        const res = await fetch(`${API_BASE}/flights`);
        const data = await res.json();
        allFlights = Array.isArray(data) ? data : [];
        renderFlights();
    } catch(e) { console.error('Failed to load flights:', e); }
}

F3. API 参数错误返回 HTTP 200 — 前端白屏 P1 API 语义

web.py:174-175, 214-215
if not _validate_date(date_str):
    return {"error": "Invalid date format. Use YYYY-MM-DD"}  # HTTP 200 返回错误 dict

前端 allFlights = await res.json() 拿到的是 {"error": "..."} 而非数组，随后 flights.filter(...) 抛 TypeError，页面静默白屏。路由级 404 已正确使用 _send_error(404, ...)，此处却没用上。

修复建议：让 api_flights/api_search 返回时由 handler 判断：如果是错误 dict 则调用 _send_error(400, ...)；或让 API 方法抛异常，handler 统一捕获。

F4. curses handle_key() 按键处理逻辑混乱 — filter 输入部分失效 P1 TUI

tui.py:560, 579, 583
elif ch == 27 or ch in (ord("0"),):  # 第 560 行 — 数字 0 误清 filter
    self.filter_text = ""
...
elif ch == 27:                        # 第 579 行 — 不可达分支（已被 560 捕获）
    self.filter_text = ""
...
elif 32 <= ch < 127:                  # 第 583 行 — 可打印字符过滤输入

问题汇总：(1) ch in (ord("0"),) 导致按数字 0 会清空 filter（疑似笔误）；(2) 第 579 行 elif ch == 27 永远不可达；(3) README 声称 "Type any text → Filter" 在 curses 下字母键可输入，但数字键被 mode 切换拦截。

修复建议：删除 ch in (ord("0"),)，删除第 579 行不可达分支，将 mode 切换逻辑放在过滤输入逻辑之前，确保 Esc 用 ch == 27 单独判断。

N3. COMMANDS.md 第 119 行命令语法错误 P2 文档

COMMANDS.md:119
$ python -m hkg_flight web --force
hkg_flight: error: unrecognized arguments: --force      # exit 2
$ python -m hkg_flight --force web                      # 正确

--force / --cache-dir 是全局选项，必须写在子命令之前。文档里这条会直接报错退出。

建议：把文档改成 --force web；或给 web 子命令也加一个 --force（argparse 支持父子解析器同名 dest）。

N4. --force 语义过重 — 清空全部缓存 P2 体验

cli.py:417-419 → clear_cache(confirm=True)

原建议是"绕过本次缓存"，现在实现仍是清空整个缓存目录，且 confirm=True 跳过确认。后果：--force query CX759 会连带删掉 alerts.json（告警历史）和 airlines.json（24h 缓存）。

建议：让 APIClient 支持 bypass_cache 标志（本次请求直连 API 不读缓存），--force 只切换该标志，不动磁盘。

N5. _esc() 定义但从未使用 P2 死代码

web.py:24-26

转义实际由前端 JS 的 esc() 完成，这个 Python 函数没有任何调用点。留着会让人误以为服务端也做了过滤，是安全隐患式的误导。

建议：删除；或保留并在 api_*() 返回前对字段做一次服务端净化（纵深防御更稳）。

N6. SSE 端点是死代码 — 只发心跳不推送更新 P2 功能

web.py:136-165
while True:
    time.sleep(1)
    client.write(b":heartbeat\n\n")  # 只发注释行心跳
    client.flush()

SSE 连接只在建立时发送一次初始告警数据，之后只发送心跳，永不推送航班变更。前端完全靠 setInterval(loadFlights, 30000) 30 秒轮询。README 第 107 行仍声称 "auto-refreshes via SSE"。

建议：二选一——(a) 在 Poller.refresh_today() 后通知 WebServer 推送事件；(b) 删除 SSE 端点，前端改纯轮询，更新文档。

N7. AlertManager._clear_for_key() 列表修改不安全 P2 并发

alerts.py:119-128
with self.lock:
    active = self._alerts.get("active", [])
    to_remove = [a for a in active if a.get("key") == key]
    if to_remove:
        for alert in to_remove:
            active.remove(alert)  # 修改正在迭代的列表，多条告警时可能跳过

同一 key 可能有多条告警（GATE + STAND），remove() 在遍历时修改列表可能导致元素跳过。

建议：用列表推导一次性重建：self._alerts["active"] = [a for a in active if a.get("key") != key]；self._alerts.setdefault("history", []).extend(to_remove)

N11. SSE 异常处理不完整 P2 健壮性

其他异常（如 OSError: [Errno 22] Invalid argument）会传播到 ThreadingHTTPServer 的线程异常处理，可能打印堆栈但不清理 _clients 列表中的过期引用。

N12. utils.py log() 只有日期没有时间 P2 可观测性

六、整体评价

这是一个功能明确、架构合理的项目。上一轮审查后的安全修复（XSS 转义、路径穿越防护、本地绑定）做得扎实。主要技术债集中在三个方面：

  • TUI curses 版交互不完整 — filter 输入和按键处理存在 bug，影响日常使用
  • Web 前端缺乏健壮性 — 无错误处理、SSE 是空壳、API 错误返回语义不正确
  • 代码清洁度 — 重复函数、死代码、未使用导入积累较多，需要一次性清理

按上述优先级 1→6 逐步修复，项目可以稳定在 B 水平。当前最紧急的是 P1 四项（约 30 行改动），投入产出比最高。
