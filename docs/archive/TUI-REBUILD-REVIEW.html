01结论摘要

诊断部分：认可

第 01/02/07 节对现状的描述与代码一致。15 项可核查断言全部属实，没有发现虚构、夸大或"把推测写成事实"的情况。这部分可以直接当作事实基础使用。

节奏：有分歧

路线表里缺一档——先花 0.5–1 人日修掉三个已确认缺陷。报告把"止血"和"全功能零依赖 curses 重写"混为一谈，等于用 9–15 人日的方案去解决 1 人日能缓解的疼痛。

依赖与兼容：需补充

"可选依赖"的代价被低估，Python 3.7 的 compileall 归属未定，Windows 下快照测试策略缺失，告警未读数的派生方式是设计空白。六个问题需在 G0 前回答。

报告内部：两处冲突

第 07 节要 cache_saved_at，第 08 节说"不改缓存格式"；迁移表说参数"保持含义"，实际裸入口并不接受 --no-poll。两处都需要写死取舍。

但报告漏了三条比已列出项更硬的证据，建议补进第 02 节

  1. cli.py 的 TUI 路径从未清理任何资源。 tui 分支与默认分支都没有 try/finally，poller.stop() 与 web_server.stop() 在整个文件里一次都没被调用。按 W 开过 Web 再按 Q 退出，端口仍被 daemon 线程持有。这比"缺少统一的 TUI 会话 finally 清理"的措辞严重得多，应当作为"必须重建生命周期"的头号证据。cli.py:655-692
  2. Poller 的告警比对段在锁外读取共享状态。 refresh_today() 在第 103–110 行遍历 self.today_records 构建 old_map，但这段代码在 with self._lock 之外，与 UI 线程的 get_today() 构成真实竞态。报告提出的"原子防御性快照"必须明确覆盖这里，而不只是覆盖写入。poller.py:103-114
  3. FVM 融合是死代码，REG 恒为空。 cli.py:_merge_fvm_data() 定义了但没有任何调用点；旧 TUI 表格有 REG 列，数据源却永远不提供 registration。所以"REG Not provided"不是偶发缺失，是恒定状态。首版与其展示一个恒为"未提供"的字段，不如直接不显示 REG 列。cli.py:227-246, tui.py:414

03主要分歧：路线表里缺了一档

报告给了 A/B/C/D 四条路线，但没有"先止血"。我核对后发现，最痛的两类问题在现有 curses 实现里改动都很小。

这不是反对重建，而是反对用重建去解决可以立刻缓解的疼痛。上述三处的产出（snapshot()、version、统一清理）恰好也是新架构的地基，做止血不会浪费。更重要的是：先跑几天修好的版本，你再判断"Textual 到底解决了什么"，判断会准得多——那时可能发现剩下的问题用 1 人日也能收尾，也可能确认非重建不可。两种结果都比现在直接投 9–15 人日要好。

04六个必须在 G0 之前回答的问题

这些问题报告要么没提，要么留到了 G4。但它们的答案会改变架构，晚答的代价很高。

Q1

Textual 最终会不会进入默认安装路径？

阻塞架构决策
为什么现在要答
报告说"可选依赖 .[tui]"，但 G4 又要"让 auto 优先选择新界面"。一旦 auto 优先，绝大多数用户会装上 Textual 整条依赖链（rich / markdown-it-py / pygments / platformdirs…），"零依赖"这个卖点实际就放弃了。
建议
G0 就给出结论并写进 README 项目定位，而不是留给 G4。如果答案是"会"，那第 08 节的依赖政策措辞需要整体改写。
Q2

Python 3.7 的 compileall 如何归属？

会让 CI 红灯
为什么现在要答
CI 的 python -m compileall -q hkg_flight 会扫到 hkg_flight/terminal/*.py。报告一边要求"新版 UI 源码尽量保持可解析"，一边允许 Textual 的现代写法，这两条会在 3.7 job 上直接打架。
建议
二选一并写死：按目录拆分 compileall 扫描范围，或明确哪些文件移出扫描并加注释。现在"尽量保持可解析"会变成偶发红灯。
Q3

告警未读数怎么派生？

设计空白
为什么现在要答
new_flag 是消费型的（consume_new_flag 读后即清），报告又说"不消费共享 new_flag 去影响其他消费者"。那 TUI 只能自己比对 active 列表，但报告没写清怎么比对、以什么为幂等键。
建议
为 UI 增加一个只读版本计数器，比复用 new_flag 干净，也避免与 Web 端互抢。另外注意 _clear_for_key 会在航班 departed/landed/cancelled 时自动清除告警，活跃集合随时间自然衰减——多数时候第四页是空的，这个现实应该影响"第四页"的定位。
Q4

Esc 到底有几层语义？

契约自相矛盾
为什么现在要答
"依次关闭覆盖面板 → 清除筛选 → 返回前一主页面 → 无操作"里，第三层需要一个页面历史栈；但 1/2/5/6 被定义为平级主页面，且航司页 Enter 自带返回逻辑，两套返回机制并存。
建议
砍掉第三层：Esc 只保留"取消输入 / 覆盖"与"清除筛选"两个语义，切页只用数字键与航司页 Enter。少一层状态，帮助文本和测试都更好写。
Q5

Windows 上的尺寸快照怎么断言？

测试会 flaky
为什么现在要答
A6 要求"真实框架定尺寸快照 + resize 交互"。Textual 快照在 Windows 与 Linux 下存在行尾与宽度计算差异，写成字符串相等断言在 Windows CI 上必然间歇失败。
建议
字符串快照断言只在 Linux CI 跑；Windows CI 降级为"不抛异常 + 关键字段存在"的结构断言。另外 40 列下报告自己的 header（HKG 09-09 | CACHE / STALE）已接近挤爆，建议 G0 实测后上调最小宽度门槛。
Q6

时区问题要不要就地解决？

影响目标用户
为什么现在要答
today_str() 取系统本地日期。用户在 UTC+0 查询时，23:00 UTC 会拿到"明天"的香港数据。对项目目标用户（在香港以外查 HKG）这是常态而非边缘情况。
建议
报告的保守处理（显示偏移、不称 HKT）我认可，但应标为高优先级后续项而非普通排除项，并在 G0 记录结论与理由。

05两处内部约束冲突

冲突一：cache_saved_at 与"不改缓存格式"

第 07 节要求快照携带 cache_saved_at，第 08 节承诺"不修改缓存格式"。现实是 cache.cache_age_minutes() 基于文件 mtime，缓存年龄总是可测——因此报告设计的 UNKNOWN AGE 分支几乎永远触发不到，而"mtime ≠ 数据生成时刻"这个真正的语义问题却仍在。

建议写死取舍：cache_saved_at 取自文件 mtime，不动缓存 JSON 结构；界面措辞用"缓存写入时间"而不是"数据生成时间"。把这个决定写进报告正文，别留给实现者现场发挥。

冲突二：参数"保持含义"与实现不符

迁移表称 --cache-dir / --force / --port / --no-poll "保持含义"。实际后两个只定义在 tui 子解析器上，裸 python -m hkg_flight --no-poll 现在是 argparse 直接报错。对裸入口而言这是新增能力，不是保持。

建议：在迁移表中注明哪些是"保持"、哪些是"新增"，避免验收时按"保持"去测一个本来不存在的参数。

# 现状
python -m hkg_flight tui --no-poll      # 可用（tui 子解析器）
python -m hkg_flight --no-poll          # argparse error: unrecognized arguments

06Prompt 与批准记录

第 12 节的单行 Prompt：建议改为"报告即规范"

现在这版 600+ 字的单句把所有约束（no-poll、日期、限速、Unicode、NO_COLOR、非 TTY、退出清理、禁止提交……）压在一起。经验上，超长单句在长上下文执行中后半段约束最容易丢失——而"禁止自动提交""不得改缓存格式"恰好好在最后。

建议 Prompt 只保留一句指向性指令，让约束留在文档里由执行者回读：

请在 O:\lyh\Projects\hkia\hkg-flight-data-v3 中按 TUI-REBUILD-REPORT.html 执行 G0→G4：
第 11 节六个决策视为已批准，第 10 节为验收标准，第 03 节与第 08 节分别为范围与兼容边界，
不得越界实现未批准功能。执行前先完整阅读该报告，并在每个阶段退出时逐条回读对应验收项。

批准记录应落在仓库里

报告第 11 节说"批准前不实施"，但目前"谁批准了什么"只存在于对话里。建议在 .agents/notes/proposed/architecture/2026-09-09-tui-rebuild.md 追加一条：已批准 / 批准人 / 日期 / 批准的偏离项。否则三个月后没人能重建这个决策。
