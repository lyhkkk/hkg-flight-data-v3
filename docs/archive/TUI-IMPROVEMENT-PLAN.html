HKG Flight Data v3 · Design Review

TUI 改进建议

这份文档整理当前 curses TUI 与 simple TUI 的功能、显示、交互和测试问题，并给出分阶段改进方案。目标不是重写 TUI，而是在保持现有功能的前提下，让机场航班看板更清晰、更可靠、更容易操作。

检查对象：hkg_flight/tui.py 包含：curses TUI + simple TUI 原则：先修功能，再优化显示 状态：建议阶段，尚未实施

一、结论摘要

P1 · 功能正确性

页面导航应统一

告警和航司页面目前使用阻塞式 getch()，按任意键就返回离港页，体验与主列表不一致。建议改为真正的模式状态，由主循环统一处理按键。

P1 · 数据可见性

后台更新要主动反映

Poller 在后台更新数据后，TUI 不一定立即刷新。建议根据 last_update 变化触发重绘，并在标题栏显示更新时间与数据来源。

P2 · 使用体验

航班行压缩并适配宽度

当前固定字段约需 80 列，包含 REG 后容易挤满窄终端。建议默认隐藏 REG，缩短路线，并按终端宽度保护核心字段。

二、当前功能盘点

功能当前按键/行为现状建议
离港航班1可用保留，作为默认页面
到达航班2可用保留

四、按优先级的改进建议

P1

统一页面导航

当前问题：cmd_alerts() 和 cmd_airlines() 在渲染后直接调用 getch()，用户按任意键即返回离港页。

建议：仅切换 self.mode，由 run() 和 handle_key() 统一管理。

1  Departures
2  Arrivals
5  Alerts
6  Airlines
Esc  返回上一模式
Q  退出（所有模式有效）
P1

后台数据更新后刷新画面

当前问题：Poller 在后台更新 today_records，界面缺少明确的自动刷新和数据来源提示。

建议：记录上次已渲染的 poller.last_update；当时间戳变化时刷新列表。

Updated 20:18:04 | Polling ON
Updated 20:18:04 | Cached data
No data available
P2

压缩并适配航班行

当前表格包含 TIME、FLIGHT、REG、ROUTE、STATUS、GATE/STAND、TERM，默认宽度接近 80 列。

  • 默认隐藏 REG；
  • 路线显示为 HKG→SIN；
  • 状态、路线按终端宽度截断；
  • 航班号、状态、登机门优先保留。
P2

加入清晰的搜索状态

当前所有可打印字符都可能进入过滤器，数字快捷键与筛选输入存在认知冲突；cmd_search() 也没有明确按键绑定。

建议使用 / 或 S 进入搜索，底部显示 Search: CX759_，Enter 确认，Esc 清除。

P2

实现上下滚动

文档描述了 ↑/↓ 滚动，但当前实现只处理左右翻页和 Home/End。建议为告警、航司和小终端航班列表增加统一的垂直滚动。

↑ / ↓ 逐行+← / → 翻页+Home / End 首尾
P2

显示 Web 状态和更新时间

用户需要知道数据是否正在轮询、是否来自缓存，以及 Web 服务是否已启动。

Departures | 408 flights | Updated 20:18:04 | Polling ON | Web OFF

五、页面专项建议

告警页面

  • 最新告警优先；
  • 格式压缩为 ⚠ CX759 GATE 62→63 Boarding；
  • 支持 ↑/↓ 滚动；
  • 底部显示 Alerts 1-8/15；
  • Esc 返回前一页面；
  • 状态过长时截断，不让单条告警破坏布局。

航司页面

  • 当前只显示 airlines[:h - 2]，剩余项目不可见；
  • 加入上下滚动或分页；
  • 显示 Airlines 21-40/89；
  • 后续可支持按 IATA 代码或名称筛选；
  • 数据加载失败时显示明确提示，而不是空白页面。

小终端和窗口变化

  • 保留当前最小尺寸保护；
  • 继续处理 KEY_RESIZE；
  • 宽度不足时优先隐藏/压缩 REG 和路线；
  • 避免直接按字符数截断宽 Unicode 字符导致错位；
  • 表头和数据行使用同一套列宽计算。

simple TUI

  • 短期不要求与 curses 完全一致；
  • 至少统一 1/2/5/6/N/P/Esc/Q；
  • 保持 NO_COLOR 和非 TTY 安全输出；
  • 文档明确说明 simple TUI 的能力差异；
  • 避免告警和航司页面使用“按任意键返回”这一隐式行为。

六、建议的数据刷新流程

Poller 拉取数据
→
更新 last_update
→
TUI 检测时间戳
→
刷新当前模式
→
保留页码/筛选

建议不要无条件每秒重绘完整屏幕。输入超时只用于检查退出、窗口变化和后台更新；只有数据时间戳、窗口尺寸或当前输入发生变化时才重绘。

测试类别应覆盖的行为优先级

八、推荐实施顺序

  1. 统一告警/航司页面的非阻塞导航和 Q/Esc 行为。
  2. 让 TUI 对 Poller 的新数据进行可见刷新，并显示更新时间/缓存状态。
  3. 实现上下滚动，修正文档中 ↑/↓ 与实际代码的不一致。
  4. 压缩航班列表布局，默认隐藏 REG 并增加终端宽度适配。
  5. 设计明确的搜索模式，解决快捷键与筛选字符冲突。
  6. 补充 FakeCursesScreen 按键、布局、刷新和模式切换测试。
  7. 最后再统一 simple TUI 的交互细节。

最终建议

不要一次重写整个 TUI。第一轮优先解决“页面是否能正常返回”和“用户看到的数据是否最新”这两个功能问题；第二轮再优化航班行和终端宽度；第三轮统一搜索、滚动和 simple TUI。每一轮都配套 FakeCursesScreen 回归测试，避免再次出现“文档描述了按键，但代码没有实现”的问题。
