一总体结论

报告的方向是对的——非阻塞模式、刷新机制、宽度适配这三条抓到了真问题，测试章节尤其扎实。但它更像一份"看起来都对"的 UX 提案，而不是基于代码的诊断：三个最严重的问题被定性轻了，四条真实缺陷完全没提，两处建议在当前代码里落不了地。如果照着这份文档排期，第一轮做完用户会发现"页面能返回了，但数据还是旧的"。

三定性过轻的三处

严重 · 症状判断错误

1. 告警页不是"按任意键返回"，而是 1 秒后自动关闭

报告原文："cmd_alerts() 和 cmd_airlines() 在渲染后直接调用 getch()，用户按任意键即返回离港页。"

构造函数里设了 stdscr.timeout(1000)，因此 tui.py:504 的 getch() 最多阻塞 1 秒就返回 -1。结果是不管用户按不按键，页面都会在一秒内自己退回离港页——用户根本来不及读完一条告警。

# tui.py:257
stdscr.timeout(1000)  # 1 second timeout for polling

# tui.py:500-505
def cmd_alerts(self):
    self.mode = "alerts"
    self.render()
    self.stdscr.getch()   # <= 1s 后返回 -1，不是阻塞等待
    self.mode = "departures"

这不是交互设计问题，而是把"轮询超时"误用成了"阻塞等待"。报告的实施顺序第 1 条应当明确写入修复这一点。

严重 · 根因判断错误

2. 数据不是"刷新不及时"，而是永不刷新

报告原文："Poller 在后台更新 today_records，界面缺少明确的自动刷新和数据来源提示。" → 建议"记录上次已渲染的 poller.last_update，当时间戳变化时刷新"。

真正的原因在引用语义上：load_view() 拿到的是 poller 列表对象的引用，而 Poller.refresh_today() 是重新绑定 self.today_records = new_records。TUI 手里永远是启动那一刻的旧列表；visible_flights() 又只在列表为空时才重新加载，所以数据一旦首次加载成功就再也不会变。

# tui.py:267 —— 只取一次引用
self.today_records = self.poller.today_records

# poller.py:112-114 —— 这里是重新绑定，不是原地修改
with self._lock:
    self.today_records = new_records
    self.last_update = datetime.now()

仅比对 last_update 治不了这个病：时间戳会变，但 TUI 仍持有旧列表。正确顺序是先重新取 poller.today_records，时间戳只作为触发条件。另外补充一点：poller.last_update 目前在整个 TUI 里没有任何读取方。

严重 · 优先级错配

3. 数字键冲突不是"体验不明显"，是航班号打不出来

报告原文：筛选"可用但不明显"，并建议用 / 进入搜索模式，列为 P2 第 5 步。

handle_key() 中 1/2/5/6/W 的分支排在可打印字符分支之前，因此这些字符永远不会进入筛选串。后果是 CX261、HX535 这类航班号根本无法输入——而按航班号查找正是航班看板最主要的操作。

# tui.py:536-564
elif ch == ord("1"):  self.set_mode("departures")   # 1 被截走
elif ch == ord("2"):  self.set_mode("arrivals")     # 2 被截走
elif ch == ord("5"):  self.cmd_alerts()             # 5 被截走
elif ch == ord("6"):  self.cmd_airlines()           # 6 被截走
elif ch in (ord("w"), ord("W")): self.cmd_web()
...
elif 32 <= ch < 127:  self.filter_text += chr(ch)  # 永远到不了这里

这属于功能阻塞，应进 P1；放在 P2 第 5 步，等于让这个 bug 多活两个迭代。

同类偏差：报告说 curses 下筛选"不够明显"，实际情况更糟——_render_flights() 完全没有渲染 filter_text（simple TUI 反而会打印 Filter: '...'），用户是在盲打。

四报告遗漏的问题

遗漏

航司页每次渲染都发网络请求

_render_airlines() 直接调用 api.fetch_airlines()；缓存失效或无缓存时这是一次同步 HTTP，被放在渲染路径上。航司模式下每按一次键就可能触发一次请求。

tui.py:460

遗漏

首屏无数据时，每次按键触发同步请求

visible_flights() 发现 today_records 为空就调用 load_view()，而后者会同步 api.fetch_flights()。API 不通时，界面会每一次按键都卡住数秒。

tui.py:281-282

遗漏

cmd_search() / prompt() 是死代码

handle_key() 中没有任何分支调用 cmd_search()，它从未被执行过。报告建议"给它明确的按键绑定"，却没说明它当前不可达。附带隐患：prompt() 中 addstr(h-1, 0, label.ljust(w)) 写满最后一行会抛 curses 异常。

tui.py:471-498

遗漏 · 前置依赖

"数据来源"字段根本不存在

报告要求显示 Cached data，但 Poller 只在日志里写"Using cached data"，对象上没有可读取的来源标记——last_update 无论走 API 还是走缓存都会更新。要显示来源，必须先给 Poller 增加 last_source，这是一处前置改动。

poller.py:93-94, 112-114

五方案自身的漏洞

自相矛盾

Esc 键被赋予两种语义

P1 导航一节写"Esc 返回上一模式"，P2 搜索一节写"Esc 清除筛选"。而当前代码与 README 都是"清除筛选"。必须先定优先级，否则实现阶段必然返工。

README.md:116 · tui.py:547

方案悬空

REG 移出后无处安放

报告建议"REG 可放入详情视图"，但 TUI 压根没有详情视图（只有 CLI 的 --details）。要么直接砍掉 REG，要么把"新建详情视图"单列成一项任务。

缺少断点

给了字段优先级，却没给降级规则

报告给出核心字段优先级，但没说 60 列砍什么、40 列砍什么；而测试计划又要求覆盖 40/60/80/120 列。实现者只能自己拍脑袋，测试结果也无从判定对错。

与 SPEC 冲突

目标界面与项目自身的规格书不一致

SPEC.md 第 163 行写的是 [1]Search [2]ByDate [3]Departures [4]Arrivals，而报告的目标界面沿用代码的 1=Dept / 2=Arr，却未指出这处文档与代码的不一致。同理 SPEC.md 第 175、191 行仍在写 ↑/↓ 滚动（README 已修正），说明上一轮文档修复只做了一半。

SPEC.md:163, 175, 191

六报告中判断准确的部分

值得保留
  • 统一页面导航：确实应把 mode 切换与按键处理收敛到 run() / handle_key()，这是全篇最有价值的一条。
  • 压缩航班行：当前固定列宽合计约 83 列（含 REG），在 80 列终端必然溢出，判断属实。
  • 航司页只显示当前屏幕：airlines[:h - 2] 之后的项目完全不可见，描述准确。
  • 测试章节：全篇最扎实。FakeCursesScreen 已存在，当前 TUI 只有 2 个用例（仅覆盖告警/航司渲染与 filter 输入/退格/清除），补测试的方向判断准确，可以直接执行。
  • 分三轮推进、每轮配套回归测试：节奏合理，应当保留。

七建议对报告做的修订

  1. 把"数据永不刷新"与"航班号无法输入"提到 P1；P1 第 2 条补明根因是引用快照，而非刷新时机。
  2. 实施顺序第 1 条补上"修复 1 秒自动关闭（timeout 误用）"——这是当前用户最能直接感知的症状。
  3. 新增一节"前置依赖"：Poller 增加 last_source；航司数据改为缓存优先且移出渲染路径；today_records 为空时增加退避策略。
  4. 明确 Esc 的唯一语义，并给出 40 / 60 / 80 列的具体列裁剪表。
  5. 补一句：本次改动需同步修正 SPEC.md 第 163、175、191 行，避免再次出现"文档写了、代码没有"。
